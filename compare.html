CareCall vs CareCall Screens

Same stack. Same design. One broadcasts to everyone. The other whispers only to the right room.

The Origin Story

Why Two Separate Repos?

CareCall started as a single-room solution. As multi-room clinics adopted it, a new need emerged — room isolation. Rather than complicate the simple version with optional keys, we built a focused v2.

Message Flow

What Travels Over the Wire

CareCall — Single Broadcast

① Doctor sends a call
{ "type": "call", "number": "7" }
② Server broadcasts to ALL clients
{ "type": "state", "cause": "call", "announcement": { "number": "7", "sentAt": 1700000001000 }, "onlineCount": 3 }
③ On connect — state snapshot
{ "type": "state", "cause": "sync", "announcement": { "number": "7", "sentAt": … }, "onlineCount": 3 }
④ Presence update
{ "type": "presence", "onlineCount": 4 }

CareCall Screens — Key-Targeted

① Doctor sends a call (with key)
{ "type": "call", "number": "7", "key": "101" }
② Server broadcasts only to key "101" clients
{ "type": "state", "cause": "call", "key": "101", "announcement": { "number": "7", "key": "101", "sentAt": 1700000001000 }, "from": "dr" }
③ Doctor switches room key (no reconnect)
{ "type": "setKey", "key": "102", "role": "dr" }
④ Presence — scoped to the key
{ "type": "presence", "key": "101", "onlineCount": 2 }
The Key Concept

How Room Key Pairing Works

A "key" is any string — a room number, a doctor's name, a department code. The server groups WebSocket clients by their key and only routes calls within that group.

1

Doctor opens /dr/ — Key Modal appears

On first visit, the browser shows a modal: "Enter your Room Key". Doctor types 101 and taps Save. The key is written to localStorage.

2

Browser opens ws://server/ws?key=101&role=dr

The server reads ?key=101 and ?role=dr from the URL. It calls registerClientKey(ws, "101", "dr") — adding this WebSocket to the connectedKeys["101"] Set.

3

Display TV opens /display/ — enters same key

The same modal appears on the display. Staff enters 101. Display connects to ws://server/ws?key=101&role=display. Now both are in the "101" bucket.

4

Doctor dials token 7 → taps Send

Browser sends {"type":"call","number":"7","key":"101"}. Server calls setCurrentCallForKey("101","7") and broadcastToKey("101", state). Only clients in key 101 receive it.

5

Display (key:101) updates and speaks

Token 7 appears on the TV screen. Telugu audio plays: "నంబర్ ఏడు". Elapsed timer starts. Display (key:102) is completely unaffected.

6

Doctor taps 🔑 Key badge → changes to Room 102

Modal opens pre-filled. Doctor types 102. Browser sends {"type":"setKey","key":"102"}. Server moves the WebSocket from key 101's bucket to 102's — no page reload, no reconnect.

Decision Guide

Which One Do You Need?

Use CareCall (V1) if…
  • 🏥 Single consultation room — one doctor calling
  • 📺 Multiple TVs, same content — hall TV + corridor TV show the same number
  • ⚡ Zero setup preference — no key management needed
  • 📱 You want multiple mobile UI variants to choose from
  • 🔁 Simplest possible stack — fewer moving parts
Use CareCall Screens (V4) if…
  • 🏥 Multiple consultation rooms — Room 101, 102, OPD, Lab
  • 📺 Each room has its own TV — Room 101's TV should NOT show Room 102's calls
  • 🩺 Multiple doctors working simultaneously
  • 🔑 Doctors move between rooms — key-switch without reconnecting
  • 📊 Doctor needs to see paired screen count

💡 Can you run both at the same time?

Yes. They are completely independent servers on different ports (3001 and 3002). A clinic can run CareCall for the main waiting hall (all TVs show same call) and CareCall Screens for the specialist consultation wing (each room isolated). Both run on the same laptop simultaneously.
